Black October: Inside the PHP2Shell vulnerabilities

A research-led breakdown of the cybersecurity events that made October 2026 stand out — with a deeper look at how two critical flaws in PHP's runtime could turn an ordinary web request into a server-level security incident.

RESEARCH & EXPLAINEROCTOBER 2026FOCUS: PHP RUNTIME SECURITY
01 / THE CONTEXT

Why “Black October”?

Black October was an informal label used to describe a cluster of high-impact cybersecurity disclosures and incidents that surfaced around October 2026. It was not one coordinated attack or a single vulnerability. The month brought attention to weaknesses across widely used software, infrastructure and digital trust systems. PHP2Shell became one of the most prominent stories because the issue sat inside the PHP runtime — a foundational layer used by a large number of web applications.

THE BROADER PICTURE

Many layers, one busy month

Security teams were responding to critical software vulnerabilities, supply-chain concerns, certificate trust issues and AI-enabled cyber activity. Each incident required its own investigation and response.

OUR DEEP DIVE

Why PHP stood out

PHP is embedded in the server-side stack behind many websites and content-management systems. A flaw in the runtime can affect applications even when their own code has no obvious vulnerability.

IMPORTANT DISTINCTION

“Black October” is the wider cybersecurity context. PHP2Shell is the specific technical issue explored in depth in this case study.

02 / THE FOUNDATION

First, what is PHP?

PHP is a server-side scripting language. When a browser requests a page, a web server can pass the request to PHP, which executes application logic and returns a response — often HTML or data for the browser. PHP is commonly used in websites, content-management systems and web applications.

01 · REQUEST

A user visits a website

The browser sends an HTTP request to the web server. The request may contain form fields, cookies, uploaded files or other data.

02 · RUNTIME

PHP processes it

The PHP runtime interprets and executes the server-side code, manages memory and handles the request lifecycle.

03 · APPLICATION

The application responds

The application may read or update data, apply business logic and generate a response.

04 · RESPONSE

The browser receives output

The server sends the response back to the user. The browser does not normally see the internal PHP execution.

This simplified flow explains the role of the runtime; real deployments may include PHP-FPM, web-server modules, reverse proxies, containers and other infrastructure.

03 / THE INCIDENT

PHP2Shell: when the runtime itself becomes the attack surface

PHP2Shell refers to two critical vulnerabilities in PHP's core runtime: CVE-2026-109618 and CVE-2026-109619. Under vulnerable conditions, specially crafted HTTP traffic could trigger unsafe memory-handling paths and potentially lead to unauthenticated remote code execution, information disclosure or denial of service.

Both rated Critical in the cited advisories
CVE-2026-109618

Incomplete initialization after memory exhaustion

When PHP runs out of memory, request processing can be interrupted before some internal request data is fully initialized. During cleanup, PHP may incorrectly treat that incomplete data as valid.

CVE-2026-109619

Stale references to freed memory

A fatal error can leave internal state referring to memory that has already been released. A later request handled by the same worker may encounter that stale state before it is reset.

WHY THIS MATTERS

The weakness is in PHP's runtime, not necessarily in a particular website's business logic. Updating a CMS theme or application plugin alone does not repair a vulnerable PHP runtime. The runtime or vendor-provided package must be patched.

04 / UNDERSTANDING THE RISK

From a malformed request to a serious impact

At a high level, the attack path starts with a request crafted to trigger an exceptional condition in PHP's request-processing or memory-management logic. If the vulnerable path is reached, unsafe memory handling can create an opportunity for an attacker to affect the PHP worker.

Reach the runtime

An attacker sends a specially crafted HTTP request to a server that processes requests using a vulnerable PHP version.

Trigger an error path

The request causes a condition such as memory exhaustion or a fatal interruption during request processing.

Unsafe memory handling

Incomplete internal state or references to freed memory may be used during cleanup or by a subsequent request.

Potential security impact

Depending on the conditions and exploitability, outcomes can include process crashes, information disclosure or remote code execution.

This is a conceptual explanation, not an exploit walkthrough. Successful exploitation depends on runtime, configuration and deployment conditions; impact should not be overstated as automatic full server compromise.

05 / RESPONSE & REMEDIATION

What did the response involve?

21 OCTOBER 2026

PHP published security updates addressing the two vulnerabilities. The coordinated disclosure timeline was accelerated after details began circulating ahead of the planned release.

PATCH RELEASES

Upstream fixes were released in PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35. Operators on older branches were advised to check distribution or hosting-provider security updates and supported upgrade paths.

DEFENCE IN DEPTH

Cloudflare described deploying Web Application Firewall protections to block known exploit traffic. These protections can reduce exposure but do not replace patching the vulnerable runtime.

VERIFY, NOT JUST INSTALL

Organisations need to identify every PHP deployment, apply the correct vendor patch, restart affected services where required, verify the running version and review relevant logs for signs of suspicious activity.

PATCHING PRINCIPLE

Confirm the actual package and vendor advisory for each environment. A vendor may backport a security fix without using the exact upstream version number shown above.

06 / RESEARCH PROCESS

How we broke down the issue

The goal was not to reproduce the vulnerability or claim original security research. It was to understand a complex technical disclosure well enough to explain the issue accurately to a non-specialist audience.

Start with the fundamentals

Understand PHP's role in a web request before trying to explain a runtime-level vulnerability.

Separate the two CVEs

Compare the root cause and failure condition described for each vulnerability instead of treating PHP2Shell as one generic bug.

Cross-check the claims

Compare vendor and researcher write-ups for severity, affected components, impact and patch guidance. Keep uncertain or deployment-specific claims qualified.

Translate without oversimplifying

Use a request-lifecycle explanation and plain-language analogies while preserving the technical distinction between incomplete initialization and stale memory references.

WHERE AI FITTED IN

AI tools supported research exploration, summarisation, terminology clarification and drafting. They were treated as assistants, not authorities: technical claims still needed to be checked against primary advisories and credible security research. This work was an independent explainer, not vulnerability discovery, exploit development or a penetration test.

07 / TAKEAWAYS

What this research reinforced

01

Security exists below the application layer

Secure application code cannot compensate for a vulnerable runtime or infrastructure dependency underneath it.

02

Asset visibility is foundational

Teams cannot patch what they do not know they run. Inventory across hosts, containers and vendor-managed environments matters.

03

Mitigation is not remediation

WAF rules and temporary controls can help reduce risk, but they are not substitutes for fixing the underlying software.

04

AI increases the pace of security work

AI can help researchers analyse code and explore attack paths, but human verification, coordinated disclosure and disciplined patching remain essential.
